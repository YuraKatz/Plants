## 4. Точки расхождения (где ты должен решить)

### A. Obsidian как core engine — да или нет?

**Gemini:** «Выкинь Python и Jinja вообще. Каждое растение/грунт/удобрение — markdown-файл с YAML frontmatter. Dataview собирает таблицы запросом. Obsidian Mobile + Syncthing = нативный ввод с телефона + полный оффлайн.»

**Я и Codex:** против. Аргументы:
- Текущий стек работает, миграция = месяцы работы
- Теряешь машинообработку (твой `api/*.json`, доступный для AI)
- Dataview — мощный, но vendor-lock в Obsidian
- Версионирование через git ты уже имеешь

**Что это даст тебе по линзе value:**
- Если **главная боль = ввод с телефона** → Obsidian реально решает (нативный mobile-first markdown editor с Git)
- Если **главная боль = мгновенный ответ для AI и публичность сайта** → текущий стек выигрывает

**Рекомендация:** не сейчас. Через месяц после instant search и PWA на телефоне — пересмотреть. Если ввод данных по-прежнему болит — **попробовать Obsidian параллельно**, не отказываясь от текущего: Obsidian читает те же `data/*.yaml` (frontmatter совместим), и можно держать оба интерфейса.

### B. i18n (ru/en/he) для одного пользователя — оставить или убрать?

**Gemini красным флагом:** «Если ты один и думаешь на русском — оставь только русский. i18n убивает гибкость в 3 раза при добавлении новой фичи».

**Я и Codex:** не подняли это явно. Я воспринял i18n как уже-готовую часть.

**Текущая реальность (validator показывает):**
- 10 ключей в `ru.yaml` нет в `en.yaml`
- 173 ключа в `en.yaml` без оригинала в `ru.yaml`
- 15 ключей в `ru.yaml` нет в `he.yaml`
- 172 ключа в `he.yaml` без оригинала

= **370 рассогласований переводов**, и они **накапливаются** при каждой новой фиче.

**Что это даст тебе по линзе value:**
- en/he нужны если **другие люди** реально читают сайт. Иначе это твой долг сам себе.
- Удалив en/he, освобождаешь часы на каждую новую фичу — тратить не нужно на 3 файла переводов.

**Вопрос к тебе:** кто заходит на en/he версии? Если никого реального (только ты для проверки) — Gemini прав, можно выпилить. Если есть аудитория (показываешь иностранным коллекционерам?) — оставлять.

**Безопасный middle ground:** перевести на **lazy translation** — keys могут отсутствовать, fallback на ru. Это уже частично работает в `_translate_plants()` через `t.get(key, key)`. Тогда новые фичи добавляются только в ru.yaml, en/he догоняются по запросу — и validator перестаёт ругаться (можно сделать i18n check warning, не error).

## 6. Stop-loss (синтез из 3 голосов)

Все три эксперта дают примерно одну линию: **через 1–3 месяца** проверить:

- **Codex:** «Если за 30s не получаешь ответ оффлайн на телефоне; новые данные больно вводить; рассинхрон возвращается; идёшь в внешний AI вместо своего интерфейса» → менять архитектуру
- **Gemini:** «Если стоя у канистр всё ещё открываешь Keep/Notes, фотографируешь показания "чтобы потом занести", лень добавить препарат в базу» → UI/UX ввода провалился, идти в Obsidian (H5)
- **Я:** «Если через месяц ты по-прежнему не достаёшь PWA в момент работы» → переходить к чат-overlay (H7)

**Конкретный измеритель:** через 1 месяц после instant search — **в логах PWA должны быть события поиска**. Если нет — значит даже с поиском не пользуешься. Тогда проблема не в инструменте, а в воркфлоу.
